# Живой 3D-контроль разметки — skeleton-lines-stable

Изменения подготовлены для SugarBlend/label-studio, ветка `skeleton-lines-stable`,
базовый commit `dba985e31f46aacfd659cdcb8af01c271728c1c9`. Ничего не отправлено на GitHub.

## Что добавлено

- Settings → **3D skeleton**: четыре JSON-калибровки, размеры каждой камеры, нормаль пола, переключатель включения.
- Нумерация секторов мозаики по строкам: `0 1 / 2 3`. Файл назначается сектору вручную, а не по имени.
- Панель рядом с разметкой: вращение мышью/кнопками, зум, скелет, ориентир плоскости пола, углы стоп и ошибки репроекции.
- Живой пересчёт несохранённых точек с задержкой 200 мс; устаревшие ответы отменяются при правке/переходе между заданиями.
- API `POST /api/projects/{id}/skeleton-3d/reconstruct/` в **том же Django-приложении**, без отдельного контейнера геометрии.
- Настройки хранятся в БД проекта (новая миграция `0035_project_skeleton_3d_config`).
- Панель только читает разметку. Fit, автоматической правки точек и сохранения 3D в аннотацию нет.

## Установка исходников

Уже подготовленный локальный checkout можно использовать сразу. Если переносите пакет на другой компьютер:

```sh
git clone --branch skeleton-lines-stable --single-branch https://github.com/SugarBlend/label-studio.git
cd label-studio
git rev-parse HEAD
git apply --check /path/to/skeleton-3d.patch
git apply /path/to/skeleton-3d.patch
```

Путь к патчу замените реальным. Если ветка уже обновилась и проверка патча не проходит, **не применяйте его принудительно**: сначала согласуйте изменения с новой версией. Патч рассчитан на указанный commit.

## Сборка образа

Собирать нужно из checkout'а с изменениями — копирование отдельных `.py` или перезапуск старого образа интерфейс не обновят.

```sh
cd /opt/label-studio-skeleton
docker build --progress=plain -t label-studio:skeleton-lines-1.23.1 .
```

Тег обязан совпадать с `image:` в действующем Compose (`label-studio:skeleton-lines-1.23.1`). Иначе Compose возьмёт другой образ или попытается скачать этот тег из реестра, где его нет. Сборка с нуля занимает 15–25 минут (poetry-зависимости и frontend).

Git checkout обязателен: Dockerfile берёт версию из `.git`. Сборка требует сети и нескольких ГБ диска.

Сборка из checkout на Windows без прав на симлинки: git хранит вспомогательные скрипты `deploy/docker-entrypoint.d` как симлинки, а на такой файловой системе они превращаются в текстовые заглушки с путём. Из-за этого контейнер падал на `docker-entrypoint.d/app-init/...: No such file or directory` — то есть не доходил ни до миграций, ни до запуска. В Dockerfile добавлен шаг, который заменяет такие заглушки копией целевого скрипта; на нормальном checkout (Linux/macOS, WSL с симлинками) шаг ничего не меняет.

Проверка образа до подключения к рабочему стенду:

```sh
docker run --rm --entrypoint sh label-studio:skeleton-lines-1.23.1 -c '
  head -1 /label-studio/deploy/docker-entrypoint.d/app-init/20-wait-for-db.sh
  grep -c skeleton-3d /label-studio/web/dist/apps/labelstudio/main.js'
```

Первая строка должна быть `#!/bin/sh` (а не `../common/...`), второе число — ≥ 1: столько строк минифицированного бандла содержат код панели.

## Обновление действующего Compose

**Сначала резервная копия БД.** В этой конфигурации она лежит в каталоге данных:

```sh
cp "${LS_DATA_PATH}/label-studio.sqlite3" "${LS_DATA_PATH}/label-studio.sqlite3.bak"
```

Не используйте `down -v` и не удаляйте volumes: `down -v` уносит данные, а неверный каталог данных даёт «пустой» Label Studio.

Миграции при sqlite применяются самим `label-studio start`: `label_studio/server.py:58-62` вызывает `_apply_database_migrations()`, если БД не синхронизирована. Entrypoint при этом миграции пропускает — `deploy/docker-entrypoint.d/common/30-run-db-migrations.sh` срабатывает только при заданном `POSTGRE_HOST` или `MYSQL_HOST`. Поэтому отдельный `label-studio-migrate` в вашей схеме не нужен.

```sh
cd <каталог с вашим docker-compose.yml>
docker compose up -d --force-recreate labelstudio labelstudio-reserve labelstudio-outsource
docker compose logs --tail=80 labelstudio | grep -E "Initializing database|Starting development server|Traceback"
```

`--force-recreate` нужен, потому что тег образа не меняется, а его содержимое — да.

Если хотите зафиксировать, что образ локальный и не подлежит скачиванию, рядом с действующим Compose можно положить `docker-compose.skeleton-3d.example.yml` как `docker-compose.skeleton-3d.yml` и добавлять `-f docker-compose.skeleton-3d.yml` в команды. Он не меняет ничего, кроме `pull_policy: never` для трёх инстансов Label Studio.

Откат: вернуть прежний тег образа, пересоздать контейнеры, при необходимости восстановить копию sqlite. Добавленное поле не мешает работе прежней версии приложения.

**У каждого инстанса своя БД.** `labelstudio`, `labelstudio-reserve` и `labelstudio-outsource` не делят настройки, поэтому конфигурацию «3D skeleton» нужно задать в каждом отдельно.

## Где появляется панель

Панель — не отдельная страница и не вкладка. Она монтируется в экране разметки (`/projects/<id>/data?tab=...&task=<id>`) рядом с мозаикой: справа на широком экране, ниже мозаики на узком. Одновременно с ней меняется только компоновка — сама разметка и её координаты не сдвигаются.

Панель видна при трёх условиях:

1. контейнер запущен на новом образе (в старом кода панели нет вовсе);
2. в проекте сохранена включённая конфигурация: Settings → **3D skeleton**, четыре калибровки, включение, «Сохранить»;
3. страница перезагружена с `Ctrl+F5` — `main.js` кешируется браузером, и после обновления образа вкладка может ещё показывать старый бандл.

Диагностика по внешнему виду:

| Что видно | Что это значит |
| --- | --- |
| В Settings нет пункта «3D skeleton» | Старый образ или старый бандл из кеша |
| Пункт есть, конфигурация сохранена, панели нет | Не включена галочка или камер не ровно четыре |
| Панель есть, скелет не появляется | В кадре меньше двух размеченных суставов или точки попали не в свои сектора |
| Есть скелет, нет угла стопы | Не размечены пятка и оба пальца нужной ноги, либо точки пальцев совпали |

## Настройка проекта

1. Settings → **3D skeleton**.
2. В каждый сектор загрузите соответствующий JSON. Для ранее присланных камер соответствие было:

   | Сектор мозаики | Файл калибровки |
   | --- | --- |
   | 0, верхний левый | camera_0.json |
   | 1, верхний правый | camera_3.json |
   | 2, нижний левый | camera_2.json |
   | 3, нижний правый | camera_1.json |

   Это соответствие относится только к той записи; для другой установки проверьте его заново.
3. Укажите исходный размер изображения **одной калиброванной камеры**, не всей мозаики. Для присланных примеров использовали 1280×720. По умолчанию эти числа предложены, но не определяются автоматически из JSON.
4. Укажите нормаль пола в мировой системе калибровки. `[0,0,1]` верно только если мировая Z действительно направлена вверх. Все четыре камеры обязаны иметь общую систему координат и единицы.
5. Включите 3D, сохраните настройки, заново откройте редактор задания.
6. При движении точки скелет/углы обновляются. Без двух наблюдений сустав не восстанавливается; без трёх нужных точек стопы угол недоступен.

JSON поддерживается в формате присланных Fit3D-калибровок (`intrinsics_w_distortion`, `extrinsics.R/T`, рациональная дисторсия; T — центр камеры) или `K,R,t,dist` (t — перенос world-to-camera).

Для угла используются `l_heel`, `l_big_toe`, `l_small_toe` и аналогичные `r_` имена. Поддерживаются распространённые варианты с `left/right`, пробелами и camelCase. Для произвольных названий суставов нужно дополнить адаптер; он не угадывает анатомию по порядковому номеру точки.

## Границы первой версии

- Одна исходная **искажённая** мозаика 2×2, равные сектора без зазоров/обрезки. Уменьшение всей картинки допускается при сохранении пропорций. Уже исправленное (undistorted/new_matrix) изображение не подходит для raw-калибровки.
- Один человек в каждом ракурсе; одинаковые имена суставов. Четыре группы (по одной на сектор) допустимы, несколько людей/дубли сустава в одном секторе отклоняются как неоднозначные.
- Сектор определяется по положению точки. Точки, ошибочно поставленные в соседнем секторе, могут вызвать неоднозначность или высокую ошибку; это не автоматическое исправление разметки.
- Нормаль пола влияет на угол; нарисованная плоскость проходит через **начало мировых координат**, а не автоматически найденный физический пол.
- Угол — подписанный поперечный наклон передней части стопы. Плюс означает, что большой палец выше малого. Это не клиническое измерение заднего отдела стопы и не измерение нагрузки.
- Правдоподобный 3D и малая ошибка репроекции не гарантируют правильность угла. Разметчик должен сверяться с изображением, а не подгонять точки под желаемое число.
- Показаны численные ошибки репроекции; наложение репроекций на мозаику пока не добавлено.

## Проверки и статус

Пройдено в среде разработки:

- 13 Python unittest геометрии, включая все четыре присланные калибровки и независимую проверку проекций через OpenCV;
- 7 Node-тестов адаптера, событий, отмены устаревших запросов, CSRF/same-origin и неоднозначных групп;
- синтаксический разбор изменённых JS/JSX и компиляция новых SCSS;
- проверка Python-синтаксиса и `git diff --check`.

Команды из корня checkout:

```sh
python -m unittest discover -s label_studio/projects/tests -p test_skeleton_3d_geometry.py
node --test web/libs/editor/src/components/Skeleton3D/skeleton3d.node-test.mjs
```

В Windows sandbox тесты Node запускались с `--test-isolation=none` (Node 26), чтобы не создавать ограниченные sandbox дочерние процессы. В обычном окружении этот флаг не требуется.

11 API-тестов `label_studio/tests/test_skeleton_3d_api.py` проходят внутри контейнера: доступ по организации и проекту, скрытие чужой организации, валидация тела запроса, выключенный проект, запрет GET, сохранение конфигурации. В образе нет dev-зависимостей, поэтому перед запуском их ставят в контейнер:

```sh
docker compose run --rm --no-deps --entrypoint sh labelstudio -c "\
pip install -q 'pytest==7.2.2' 'pytest-django==4.9.0' 'pytest-mock==3.14.0' 'pytest-env==0.6.2' \
 mock freezegun 'moto>=4.2.6' 'responses==0.13.0' 'requests-mock==1.12.1' 'fakeredis~=2.26.1' && \
 cd /label-studio/label_studio && python -m pytest tests/test_skeleton_3d_api.py -q --create-db"
```

### Проверка в Docker (изолированные стенды, не рабочие данные)

Собран образ `sugarblend/label-studio:skeleton-3d`, подняты два стенда — uwsgi+nginx+postgres и отдельно ваша схема (`label-studio start`, `DJANGO_DB=sqlite`, порт 8081). Выполнено:

- миграции применяются в обеих схемах, `0035_project_skeleton_3d_config` в списке применённых; на sqlite в логе `Initializing database..`, отдельный `label-studio-migrate` не потребовался;
- `POST /api/projects/{id}/skeleton-3d/reconstruct/` возвращает 200, эхо `sequence`, восстановленные суставы и `foot_tilt`;
- синтетическая поза из четырёх реальных калибровок восстанавливается точно: позиция сустава совпала с заданной, RMS репроекции 0;
- калибровки с одинаковыми точками пальцев дают `right: null` и предупреждение о вырожденном разнесении, а не выдуманный угол;
- анонимный запрос — 401, точка с координатой 1e9 — 400, чужой/недоступный проект — 404;
- сессионный сценарий как в браузере (cookie сессии + `X-CSRFToken`) возвращает 200; запрос без CSRF-заголовка в проверенной сборке тоже принимается, а cookie `csrftoken` не выставляется — панель корректно работает и без токена;
- `/api/projects/{id}` отдаёт `skeleton_3d_config` с четырьмя камерами, страницы `/projects/{id}/data` и `/projects/{id}/settings/skeleton-3d` открываются с кодом 200;
- код панели присутствует в собранном бандле (`web/dist/apps/labelstudio/main.js`).

**Не проверено:** интерактивная работа панели в браузере (вращение, зум, живой пересчёт при перетаскивании точки), вид панели на реальной мозаике и реальных аннотациях, поведение при быстром переключении заданий. Это первая проверенная на уровне API и сборки версия, а не проверенный production-образ.

Перед массовой разметкой проверьте: сохранение настроек после перезапуска; доступ разметчика и запрет чужого проекта; один кадр с известными точками; перемещение/удаление/undo; быстрый переход между заданиями; отсутствие 3D в выключенном проекте; отсутствие сдвига 2D-разметки и совпадение углов с отдельным viewer на одинаковых данных/нормали.
